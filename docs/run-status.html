How archive recovery works

Recent searches use index or registration dates. Archive searches use publication dates from 2020 onward. The monitor checks an existing queue of unreported, abstract-bearing candidates before requesting more metadata. It does not relax the PopPK, AI, or methodology eligibility gate to fill an empty day.

Archive work is partitioned by year, source, and query. Each API session follows page cursors within its budget. An unfinished date range is split into smaller ranges and retained for the next run. Cross-run coverage uses date partitions rather than depending on a provider's cursor lifetime. Candidates remain in the queue until selected. “Pending windows” means that the configured search has not finished, not that the literature contains no eligible papers.

The default refill budget is eight API requests, two pages per date window, 200 records per page, and approximately eight minutes between request starts. Requests already in flight may finish after this budget. Searches refill when fewer than five eligible candidates remain. These are workload limits, not a guarantee of complete coverage. A completed archive cycle is rechecked after seven days when no eligible candidates remain.

When no paper is selected, one status Issue is sent for that Japan Standard Time date. The 07:20 retry continues if no paper has been delivered or a notice remains pending. Failed notices are retained and retried with stable identifiers. A later recovery can generate a paper notification in addition to that day's earlier status notice.

The main run remains scheduled for 07:00 JST. GitHub's scheduled jobs can start late; this system does not guarantee delivery at exactly 07:00. The displayed time is the actual scan start, not the scheduled time.
